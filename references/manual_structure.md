# 操作手册结构

操作手册应参照真实软件随附的操作说明编写，其目标为使读者了解软件的用途、功能与基本操作。

## 章节骨架

章节分为必备与项目自定两类。必备章节固定，一律生成，顺序不变；其余章节完全由模型根据当前项目判断，数量、名称与位置均不预设。本文档不提供可选章节清单，脚本亦不解释任何章节语义。原因在于，凡将章节写成固定清单，等同于将结构判断交回脚本，与本 skill 的核心原则相违背。

章节编号必须连续，正式章节标题使用中文大写序号，例如 `一、说明`，不得使用 `(1)、说明`。

### 必备章节

| 章节 | 内容要求 |
| --- | --- |
| 说明 | 软件定位、目标用户、业务场景和整体流程 |
| 功能特点 | 按真实功能概括 4 至 8 项，每项说明业务作用和用户可见结果 |
| 系统要求 | 用表格说明最低配置与推荐配置。Web 项目写浏览器、网络与服务访问要求；桌面项目写操作系统、处理器、内存、存储与分辨率 |
| 各功能页面 / 模块 | 按真实页面、导航入口或核心流程逐章说明，来源为 `manual_modules`。普通模块正文以 120 至 220 个中文字符为目标，复杂模块上限 400 字；截图独立保留，不为增加字数而重复背景 |
| 常见问题解答 | 3 至 5 个与本软件真实使用相关的问题及解决方法 |
| 术语表 | 解释软件名称、核心业务对象、页面模块和用户可能不熟悉的术语 |

必备章节的固定顺序为：说明、功能特点、系统要求、各功能页面 / 模块、常见问题解答、术语表。常见问题解答与术语表恒为最后两章。

`manual_modules` 为空时，不得依据 `business_features` 缺省生成模块，应停止执行并要求模型阅读真实页面与项目资料后补全。

### 项目自定章节

必备章节之外的全部章节由模型判断。某项内容是否应当独立成章，以下列三条同时成立为准：

1. 该内容在本项目中真实存在，并能指向具体证据（源码、配置、运行产物、文档或操作视频帧）；
2. 若将该内容分散写入各功能章节，将造成重复叙述或口径互相矛盾；
3. 缺少该内容将使审核员或普通读者对本软件的理解出现缺口。

三条中任缺其一即不应独立成章。判断依据只能是当前项目的实际情况，不得因「其他手册设有该章」而设立，亦不得为增加章节数量而设立。

位置由模型指定，遵循下列排序原则：概述性内容置于功能章节之前；对功能章节的支撑性说明置于功能章节之后；常见问题解答与术语表恒居末两章，任何自定章节都不得排在术语表之后。

以下为判定标准的应用示例，用于说明判断方式，**不是可选章节清单，不得逐项照搬**：

- 某软件将统计数值直接呈现给用户，若在各功能章节分别解释各数值的算法，口径极易互相矛盾。此时将全部数值定义集中于一章成立，例如命名为「指标与口径」。
- 某软件在本机保存用户数据、配置与凭据，其存放位置、写入方式与数据流向无法归入任何单一功能章节，且审核员需要据此判断隐私边界。此时单列一章成立，例如命名为「数据存放与隐私」。
- 某桌面应用的进程划分与模块职责清晰，说明其构成有助于审核员对照代码鉴别材料。此时单列一章成立，例如命名为「程序结构」。
- 项目确实存在总体设计、详细设计、测试案例等独立配套文档，以表格指向这些真实资料成立，例如命名为「相关文档」。
- 项目存在清晰的端到端串联流程，将自进入软件至完成核心任务的过程单独完整叙述一次成立，例如命名为「典型使用流程」。

不成立的示例：

- 为增加章节数量而单列「注意事项」「使用建议」一类章节，无具体证据支撑，不成章。
- 将某个功能的操作步骤自其所属模块中拆出并单列一章，该内容属该模块的正文内容，不应外提。
- 项目并无独立配套文档，却生成「相关文档」章并填入推断的文档名，属编造。

项目自定章节的内容来自 `草稿/业务理解.json` 的 `manual_extra_sections` 字段。该字段为空时不生成任何自定章节，脚本不得推断，不得缺省生成；字段中每一项的章节名、位置、正文与表格一律照模型所写渲染，脚本不解释其语义。

以上为通用要求，不是旧项目内容。生成时必须根据当前项目业务、页面入口、功能关系和用户可见控件填充内容，不得照抄用户提供的范本文案。

## 写作口径

### 正文的撰写职责

操作手册的全部叙述性正文由模型撰写，脚本不造句。此项安排是成稿质量的前提，原因在于脚本无法判断语句是否通顺、是否贴合当前项目，只能按字段套用固定句式，其结果必然是模板化的正文与偶发的病句。

职责划分如下：

- **模型负责**：说明章正文、功能特点各项正文、各功能模块章节正文、项目自定章节正文。一律写成成文段落，直接写入业务理解 JSON 的对应字段。
- **脚本负责**：章节顺序与编号、图注编号、表格渲染、页眉、段落数与字数校验、必备要素是否在正文中出现、套话与模板句式检测。

脚本不得改写模型写下的文字，包括术语替换、同义词替换与病句修补。发现问题一律报为待修正项，交由模型重写，不得静默替换。原因在于静默替换既掩盖问题，也会破坏模型有意使用的技术表述。

模型撰写正文时仍须覆盖 `manual_modules` 中记录的真实入口、可见元素、主要动作、输入与状态规则、结果反馈。这些字段在此处的作用是核对清单，供脚本校验正文有无遗漏，不是造句原料。

覆盖校验分为两级：`entry`、`visible_elements`、`operation_steps`、`feedback` 四项必须在正文中体现，未体现即为待修正项；`validation_rules`、`rationale`、`boundary` 三项以警告形式列出未被正文体现的具体条目，由模型判断是补写正文，还是该条目本就不必进入正文。

**不得为通过校验而把核对清单改写成正文原句。** 清单与正文表述不一致时，正确的处置是改写正文使其涵盖该事实，或确认该条目不必进正文而保留警告；把 `entry`、`boundary` 一类字段直接替换为正文里的句子，会使校验退化为自我印证，核对意义随之消失。正文字数上限设为 400 字，正是为使入口、动作、规则、反馈、取舍原因与边界情形能同时容纳，无须靠删减清单来迁就篇幅。

### 基本要求

- 使用通用、客观、简洁的中文。
- 不写面向终端用户的复杂教程。
- 每个章节必须有段落化说明，不能只写项目符号列表；正文不得使用 `-`、`*`、`1. 2. 3.` 罗列信息。表格用于并列且字段一致的内容，例如系统要求、路径清单、定义清单，属于正常排版，不受此限。
- 每个核心页面或功能模块正文建议写 2 个短段落，必要时可写 3 段，上限 400 字。第一段合并使用场景、页面用途、进入位置和关键页面元素；第二段说明用户动作、关键输入或状态规则和结果反馈。每个动作单独成句，删除重复背景、同义复述和泛化承接句。
- 正文通过去重、合并同类信息和简练句式控制长度，不按固定数量裁剪页面元素、用户动作、操作规则或结果反馈；不得因精简删除真实入口、主要动作或结果。
- 优先写用户真实能看到和操作的内容，例如输入框、按钮、下拉框、标签页、列表、卡片、弹窗、错误提示、状态栏、导入导出入口、额度或权限提示。
- 补充说明段落只能写当前软件的用途、业务场景、页面组织和用户流程，不写「本操作手册用于……」「面向软著审核……」「不描述代码实现……」这类解释文档写作方式的元话语。
- 页面章节不得输出「进入方式：」「页面内容：」「操作步骤：」「操作规则：」「操作结果与反馈：」这类模板小标题。
- 功能特点不得写成「开头一句总述 + 编号列表 + 结论」的头中尾结构。每个特点用段落展开，说明该功能解决什么业务问题、用户在页面上看到什么、完成操作后得到什么结果。不同功能的说明须有差异，避免各条使用相同句式。
- 不夸大不存在的功能。
- 功能名称和章节组织由模型根据项目证据判断；路由、页面、README、接口和组件命名只是证据来源，不是固定抽取规则。
- 禁止在脚本中按 auth、query、form、workflow 等分类自动生成入口、步骤或结果反馈。入口和步骤必须来自模型对当前项目真实页面的阅读。

### 设计取舍原因的说明

此项要求是使手册脱离模板、贴近真实的最有效手段，属于强制要求，不是可选润色。

凡遇到「本可以是另一种做法，而本软件选择了这一种」的情形，须在该处补一句原因，句式为「原因在于……」或「此项安排的原因在于……」。适用场景包括：

- 某项数值为何由本机计算而非交由外部服务；
- 某个目录为何另设一处而不与程序本体同放；
- 某项统计为何排除某一段数据；
- 某个限制为何只对一部分对象生效；
- 某个状态为何显示为占位符而非零值；
- 某项默认值为何取当前这一数值。

原因必须来自项目真实约束，例如运行环境限制、数据可得性、口径一致性、性能代价或用户可理解性。写不出真实原因时删去该句，不得以「为提升用户体验」「为保证系统稳定」一类空话填充。判断标准为：将该句中的软件名替换为任意其他软件后仍然成立者，即属空话，须删除或改写。

### 边界与异常状态

功能章节除正常路径外，须写明可预见的边界情形及软件的实际表现，例如：

- 依赖数据缺失时界面显示什么，以及为何不显示为零值；
- 某项前置条件未满足时哪些功能仍然可用、哪些不可用；
- 超出容量、额度或时限时软件如何处置，处置后哪些数据保留、哪些被清理；
- 关闭某项可选功能后，哪些派生能力仍然有效及其原因。

这类内容无法从代码结构泛泛推出，是审核员判断文档真实性的直接依据。

### 图与图注

- 每幅截图须有独立编号，格式为「图 <章号>-<章内序号>」，例如 `图 3-1`。
- 每幅截图下方须有一句图注，说明该图需要呈现的状态或结果，不得简单复述正文原句。
- 同一功能存在多个显著不同的状态时，分别配图并在图注中点明状态差异，例如待命、进行中、结束后。
- 尚未取得截图时，保留正式 Word 中可见的截图预留文字，并同样带编号与说明，例如：`【图 3-1 截图预留：请在此处插入「项目管理」页面列表状态的截图。】`。不得使用 HTML 注释作为占位，原因在于该形式在正式 Word 中不可见。

### 常见问题解答

- 必须写软件真实会出现的故障与提示，例如实际的报错文案、实际的权限拒绝、实际的依赖缺失。
- 每条须给出可依次执行的排查顺序，涉及具体路径、环境变量、系统设置项时照实写出。
- 禁止「若无法使用请检查网络」「如有问题请联系管理员」一类无法执行的条目。
- 故障与软件本身无关时应当写明，例如由运行环境的某个变量导致的启动异常。

### 技术性表达的边界

技术内容按所解释的对象区分，不是全文禁止。判断依据为该句所解释的对象：解释用户看到什么、操作什么、操作后得到什么，用日常语言；解释软件由什么构成、数据存放在哪里、数值如何算出、运行需要什么条件，用准确的技术语言。

据此，各功能页面章节、功能特点与常见问题解答面向普通读者，避免用代码、框架、接口、状态管理、异步任务等实现术语解释用户动作。「说明」章与全部项目自定章节不受此限：这些章节本就承担交代运行环境、技术选型、文件路径、进程划分与数值口径的职责，此类表述对登记审核有正面价值，不得因「避免技术化」而删除或改写为含糊说法。

需要注意，本条只放开技术术语，不放开套话。空泛赞美、营销口号与模板句式在全部章节一律禁止。

### 去除机器生成特征

机器生成特征主要表现为空泛、整齐、万能、缺乏项目现场感，具体形式为各模块使用同一种句式，反复写「提升效率、优化体验、提供支持」，使用「旨在、赋能、一站式、智能化、高效便捷、显著提升、强大能力、丰富功能」等口号，却没有说明当前项目的真实页面、真实对象、真实动作和真实反馈。发现这类内容时必须改写成朴素、具体、可回溯到项目证据的表达。

相近功能应结合项目真实业务分别说明各自的操作目的、用户动作和结果反馈，不能用同一段话替换不同模块。自检时必须检查是否出现同一批模块在「功能操作说明」大章下反复套用的情况；如果同一模块重复多次，必须改为每个真实页面独立成章。

### 操作视频优先

如果用户提供了操作视频，能在视频中找到对应画面的模块，其操作步骤、界面元素和结果反馈必须以模型逐帧查看 `操作视频/视频证据.md` 后观察到的真实内容为准，不能只凭业务理解或代码结构推断；截图也优先自视频抽出的帧中挑选，不必再单独截图。视频没有覆盖的模块，或用户没有提供视频时，截图前必须先让用户在浏览器自动化截图能力、桌面操作截图能力、用户自行截图三种方式中选择；选择后检查对应能力是否可用。用户说明当前不截图或先跳过截图时，记录为 `skip`，并在每个需要截图的位置保留正式 Word 中可见的截图预留文字。

## 自检记录

Markdown 草稿生成前由 agent 自行检查章节完整性、内容长度、项目流程一致性和语言自然度。发现入口、主要动作或结果缺失时回到证据补齐；发现段落过长、重复、套话、机器生成特征或章节与内容错配时先压缩和修正。完整草稿生成后只向用户发起一次整体确认，再进入 Word 生成；确认前不得进入正式 Word/TXT 生成。

操作手册生成时必须同步输出 `草稿/操作手册自检记录.md` 和 `草稿/操作手册自检记录.json`，至少包含：

- 第 1 轮：初稿生成，检查必备章节是否齐全、项目自定章节是否逐项满足三条判定标准、章节顺序与编号是否连续、截图编号与图注、模块信息完整性、正文长度。
- 第 2 轮：压缩重复背景、同义复述和泛化承接，同时保留真实流程的必要衔接。
- 第 3 轮：去除制式表达和机器生成特征，重点检查重复句式、统一套话、空泛赞美、营销口号、过度整齐的排比，以及虽属正确却无实质内容的表述。
- 第 4 轮：检查设计取舍原因与边界情形。逐条核对「原因在于」式说明是否来自真实约束、能否通过「换成别的软件是否仍然成立」的判断；核对功能章节是否写明可预见的边界情形。
- 后续轮次：如果仍有问题，继续补齐缺失信息、压缩、去重和改写，直到问题清零或记录无法自动修复的原因，不能把未修正的问题直接交给用户。

## 其他

- 禁止把测试项目中的行业、角色、流程、功能名称或示例文案写成通用规则；范本只能帮助理解软著手册需要「通顺、具体、能给审核员看懂」，不能作为固定内容来源。可参考 [worked_example_acticount.md](worked_example_acticount.md) 中「功能特点」章节模板轮换与差异化表达的真实对比案例。
- 操作手册 Word 页眉格式必须与代码材料页眉一致：左侧为「软件全称 版本号」，右侧为「第 <页码> 页」。
