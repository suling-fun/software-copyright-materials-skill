# 申请表信息字段

以下字段按官网实际表单顺序与字段名列出：

1. 软件全称
2. 软件简称（可选）
3. 版本号
4. 软件分类（应用软件/嵌入式软件/中间件/系统软件/其他）
5. 开发完成日期（YYYY-MM-DD）
6. 开发方式（单独开发/合作开发/委托开发/下达任务开发）
7. 软件说明（原创 / 修改（含翻译软件、合成软件））
8. 发表状态（已发表/未发表）
9. 首次发表日期（已发表时填写，YYYY-MM-DD）
10. 著作权人（复合字段：国家/省市/类型[自然人/法人]/姓名/证件类型/证件号）
11. 权利范围（全部权利/部分权利）
12. 权利取得方式（原始取得/继受取得）
13. 开发的硬件环境（≤50字符）
14. 运行的硬件环境（≤50字符）
15. 开发该软件的操作系统（≤50字符）
16. 软件开发环境 / 开发工具（≤50字符，格式：开发环境: xxx/开发工具: xxx）
17. 该软件的运行平台 / 操作系统（≤50字符）
18. 软件运行支撑环境 / 支持软件（≤50字符）
19. 编程语言（预设按钮选择 + 自定义输入≤120字符）
20. 源程序量（纯数字，单位行，指全部源程序总行数）
21. 开发目的（≤50字符，不能只写软件名称）
22. 面向领域 / 行业（≤50字符）
23. 软件的主要功能（500~1300字）
24. 软件的技术特点（多选标签 + 文本描述≤100字符；标签：APP/游戏软件/教育软件/金融软件/医疗软件/地理信息软件/云计算软件/信息安全软件/大数据软件/人工智能软件/VR软件/5G软件/小程序/物联网软件/智慧城市软件，都不符合时可不选）
25. 页数（代码鉴别材料实际页数）

## 字段来源与填写口径

- 软件全称、版本号、著作权人、日期：由用户确认。
- 软件全称必须显式确认；正式资料文件名、代码 Word 页眉、操作手册标题与正文中的软件名称，均以申请表信息中的「软件全称」为准。
- 软件简称：可选；存在常用简称时填写。
- 版本号必须显式确认；项目配置中的版本号小于 V1.0 时，须提醒用户软件著作权首次提交通常填写 V1.0，并由用户确认填写 V1.0 或项目当前版本号。
- 软件分类：默认选择「应用软件」。
- 开发完成日期与首次发表日期：必须使用 YYYY-MM-DD 格式。
- 开发方式：默认为「单独开发」，多人合作项目选择「合作开发」。
- 软件说明：默认为「原创」。
- 发表状态：由用户确认已发表或未发表；选择已发表时须附首次发表日期。
- 编程语言、源程序量、功能模块、技术特点：依据项目分析生成。编程语言在官网为预设按钮选择 + 自定义输入（≤120字符），预设选项包括 Assembly language、C、C#、C++、Delphi/Object Pascal、Go、HTML、Java、JavaScript、MATLAB、Objective-C、PHP、PL/SQL、Perl、Python、R、Ruby、SQL、Swift、Visual Basic、Visual Basic .Net。
- 源程序量：仅填写纯数字（不含「行」字），指登记软件全部源程序的总行数，而非代码材料的抽取行数。
- 软件开发环境 / 开发工具：≤50字符，格式 `开发环境: <OS>/开发工具: <IDE>`，例如 `开发环境: Windows 11/开发工具: Visual Studio Code`；不得填写 React、Next.js、Vite、TypeScript 等技术栈。
- 开发该软件的操作系统：≤50字符，填写实际开发所用计算机的操作系统版本。
- 该软件的运行平台 / 操作系统：≤50字符，填写软件运行所在的操作系统或浏览器环境。
- 软件运行支撑环境 / 支持软件：≤50字符，直接列出运行依赖（如 Node.js、npm、浏览器），不添加格式前缀。
- 开发的硬件环境：≤50字符，优先读取当前计算机的 CPU、内存与硬盘配置作为建议值。
- 运行的硬件环境：≤50字符，默认可沿用开发硬件的建议值，也可按实际运行设备填写。
- 开发目的：≤50字符，以一句话说明软件的开发目的，不能只写软件名称。
- 面向领域 / 行业：≤50字符。
- 软件的主要功能：500~1300字，详细描述软件核心功能，篇幅不少于 500 字。
- 软件的技术特点：多选标签（APP/游戏软件/教育软件等）+ 文本描述≤100字符；标签均不符合时可不选。

## 软件全称的商标核查

软件全称中若含有商标文字，版权中心审查时可能要求申请人提供商标注册证明，或补交一份声明，说明申请人持有该商标或已获得商标权利人授权。未事先准备的，将收到补正通知，登记周期随之延长。因此，本项核查须在软件全称首次投入使用之前完成，即 SKILL.md 第 5 步业务理解脚本运行之前；此后软件全称如有更改，须对新名称重新核查。

**识别方式**。由模型逐词审阅软件全称，判断其中是否含有品牌性文字，不得依赖脚本关键字表。须重点关注的情形如下：

- 自造词、品牌名或产品名，例如英文品牌词、中文自造词、拼音品牌词，以及项目 README、应用图标、官网、应用商店页面所使用的产品名。
- 第三方知名品牌或平台名称，例如在软件全称中写入某即时通讯平台、电商平台或操作系统的名称。
- 带有 ®、™ 等商标标识的文字。

仅由通用描述性词语构成的名称，例如「客户反馈工单管理系统」，不属于本项核查对象。判断存疑时按含有商标文字处理，交由用户决定。

**提醒用户并停止等待选择**。识别到商标文字后，须向用户指明具体是哪几个字，并说明上述审查后果，然后请用户在以下两种处理方式中选择其一：

1. **去除商标文字**：改用纯描述性名称，例如将「<品牌词>客户反馈工单系统」改为「客户反馈工单管理系统」。可另行建议一至两个候选名称，最终名称由用户确定。软件全称更改后，代码材料页眉、操作手册标题与正式资料文件名均以新名称为准。
2. **保留原名称**：适用于申请人持有该商标，或已取得商标权利人授权的情形。须提示用户准备以下任一证明：商标注册证复印件，或申请人持有该商标的书面声明。商标权利人与著作权人不一致时，另须准备商标权利人出具的授权使用证明。上述文件由用户提供，在官网填报时上传至「其他相关证明文件」。

商标仅处于申请阶段、尚未注册的，或软件全称含有第三方商标且未获授权的，建议用户去除商标文字。用户坚持保留时，须告知其可能收到补正通知，并将该告知写入确认记录。

**记录**。用户的选择写入 `application-fields` 确认点的 `--note`，注明识别出的商标文字、所选处理方式；选择保留时，另注明证明文件的本地路径或「待用户提供」。证明文件归档于 `正式资料/`，命名为 `<软件全称>-商标证明.<扩展名>`。进入官网填报后，证明文件的提供与上传状态记入 `提交记录/版权中心操作记录.md`。不得记入 `正式资料/生成报告.md`，原因在于该报告由正式生成脚本在每次运行时重新写入，手工添加的内容将被覆盖。

## 一致性要求

- 软件全称与版本号必须与代码材料、操作手册一致。
- 正式代码 Word 页眉的软件名称必须与申请表信息中的「软件全称」一致，生成 Word 时以申请表的软件全称为准。
- 正式代码 Word 页眉的版本号必须与申请表信息中的「版本号」一致，生成 Word 时以申请表的版本号为准。
- 主要功能必须来自当前项目，不得沿用范本中的旧项目描述。
- `待用户确认` 字段在正式输出前应尽量替换为确认值；若仍然存在，必须写入生成报告。
- 校验脚本对「著作权人」与「软件全称」两个字段另设占位检测，命中「示例」「XX」「Demo」「ACME」一类词即判为失败。若该词确属软件的正当名称，在工作目录下建立 `主体名称确认.json`，将 `identity_names_confirmed` 置为真并在 `fields` 中逐字记录该字段的取值，校验即转为警告并注明依据。取值与申请表不一致时豁免不生效，以防改名后旧确认继续放行。
