# 业务理解规则

申请表信息与操作手册不得仅根据代码结构泛泛生成，必须先理解软件业务。

## 证据收集

先用脚本收集证据，输出 `草稿/业务理解证据.md/json` 和 `草稿/业务理解模型稿模板.json`。证据通常包括：

- `README.md`
- `docs/*PRD*.md`
- `docs/*BRD*.md`
- `docs/*ARCHITECTURE*.md`
- 产品说明、需求文档、设计文档
- 前端页面标题、按钮文案、路由、核心组件名
- 后端 API 路由和模型名称
- `操作视频/视频证据.md`（如果用户提供了操作演示视频）：真实操作画面和顺序，可信度高于纯代码结构推断，模型必须逐帧查看后再采信

这些只是候选证据，不代表最终行业、功能和手册结构。有操作视频时，视频中观察到的真实操作顺序应优先于代码路由结构，用来判断 `operation_flow` 和 `manual_modules`。

## 输出业务理解草稿

模型必须阅读证据和必要源码，自行判断应该抽取哪些业务信息，再生成业务理解模型稿 JSON。不得用关键字表或固定模板决定行业、功能和结构；不得把用户给的范本文案、测试项目名称、测试项目流程写成通用规则。

模型稿 JSON 字段至少包含：

- `product_positioning`：产品定位
- `industry`：面向领域 / 行业
- `target_users`：目标用户
- `core_value`：用户痛点和核心价值
- `business_features` / `business_feature_details`：主要业务功能及其细节
- `operation_flow`：典型操作流程
- `application_purpose`：申请表建议口径中的开发目的
- `main_functions`：申请表建议口径中的主要功能
- `technical_characteristics`：申请表建议口径中的技术特点
- `manual_overview`：操作手册「说明」章的正文，段落数组，由模型直接撰写成文，脚本原样输出。内容为软件定位、目标用户、业务场景与整体流程；不得写「本操作手册用于……」「面向软著审核……」这类解释文档写作方式的元话语。
- `manual_feature_highlights`：操作手册「功能特点」章的正文，数组，4 至 8 项，每项含 `title`（特点名称）与 `paragraph`（该项正文，成文段落）。每项须说明该功能解决什么业务问题、用户在页面上看到什么、完成操作后得到什么结果。各项句式必须有差异，不得套用同一模板轮换。
- `manual_modules`：操作手册的核心输入，必须按真实页面、导航入口或业务流程填写，脚本不得按 `auth/query/form` 等分类模板自动补入口、步骤或反馈。每个模块必须包含：
  - `title`：页面或流程名称
  - `body`：该模块章节的正文，段落数组，2 段为常态、必要时 3 段，由模型直接撰写成文。脚本原样输出，不拼接、不改写、不做术语替换。缺失或为空时不得生成操作手册，应停止并要求模型撰写
  - `evidence`：对应页面、路由、组件、需求文档、README 或操作视频帧证据
  - `purpose`：该页面在软件中的用途
  - `usage` 或 `usage_scenario`：用户在什么业务场景下使用该页面，正在处理什么具体事务；缺少时不得生成操作手册
  - `entry`：用户从哪里进入该页面
  - `visible_elements`：用户实际能看到的输入框、按钮、列表、标签、状态或结果区域
  - `operation_steps`：按真实页面顺序写用户动作，不能写代码实现
  - `validation_rules`：必填项、长度限制、权限、额度、状态、异常提示等规则；没有则留空数组
  - `feedback`：操作完成后用户能看到的结果、提示或状态变化
  - `screenshot`：截图预留说明
  - `rationale`：该模块中「本可以是另一种做法，而本软件选择了这一种」的真实原因，用于成稿中的「原因在于……」式说明；写不出真实原因时留空数组，不得以「为提升用户体验」一类空话填充
  - `boundary`：可预见的边界情形及软件的实际表现，例如依赖数据缺失时显示什么、前置条件未满足时哪些功能仍可用、超出容量或额度时如何处置；没有则留空数组

  上列字段中，`body` 是最终写入成稿的正文，其余字段自 `evidence` 起至 `boundary` 止均为证据层与核对清单：模型据以撰写 `body`，脚本据以校验 `body` 是否遗漏真实入口、主要动作或结果反馈。脚本不再用这些字段拼装句子。

`manual_modules` 是真实证据层，应完整保存观察到的页面元素、动作、规则和反馈，不为成稿字数预先删减。操作手册渲染时通过去重、合并同类信息和简练句式控制正文长度，不按固定数量裁剪内容，并保留真实入口、主要动作和结果。
- `system_requirements`：系统要求
- `faq`：常见问题
- `glossary`：术语表
- `manual_extra_sections`（可选）：操作手册中必备章节之外的章节，由模型按项目实际情况自行判断设立，数量与名称不预设。本字段没有可选清单，脚本也不解释其语义，只按位置插入并原样渲染。字段为空时不生成任何自定章节，不得推断，不得缺省生成。设立标准见 [manual_structure.md](manual_structure.md) 的「项目自定章节」一节，三条标准须同时成立。每项包含：
  - `title`：章节名称，使用名词性短语，不写成问句或动宾短语
  - `reason`：为何本项目需要把这部分内容独立成章，须对照三条判定标准逐条说明；写不出充分理由的章节不应设立
  - `evidence`：该章内容的证据来源，例如源码路径、配置文件、运行产物、项目文档或操作视频帧
  - `position`：`before_modules`（功能章节之前）、`after_modules`（功能章节之后、常见问题解答之前）、`before_glossary`（常见问题解答之后、术语表之前）三者之一。任何自定章节都不得排在术语表之后
  - `order`：同一 `position` 内的先后次序，整数，从 1 起
  - `paragraphs`：该章正文段落数组
  - `table`（可选）：该章需要表格时填写，形如 `{"headers": [...], "rows": [[...], ...]}`，由脚本原样渲染

模型稿经脚本校验后生成 `草稿/业务理解.md` 和 `草稿/业务理解.json`，至少覆盖：

- 产品定位
- 面向领域 / 行业
- 目标用户
- 用户痛点和核心价值
- 主要业务功能
- 典型操作流程
- 操作手册说明章正文与功能特点正文
- 操作手册页面/流程模块，必须说明每个真实页面或核心流程的使用场景、进入位置、用户可见元素、用户动作、输入/状态规则、结果反馈和截图预留
- 申请表建议口径
- 证据来源
- 待用户确认项

缺少 `manual_modules` 或关键字段时必须停止，让模型回到项目证据中补写；不得用分类模板缺省生成。

## 外部调研

如果项目材料不足、业务类型较新，或用户明确希望参考竞品，可联网检索相近产品和行业资料。

外部调研只用于帮助理解行业表达，不能编造项目不存在的功能。需要把调研结论写入业务理解草稿，并区分「项目证据」与「行业参考」。

## 生成材料约束

- `申请表信息.md/txt` 的开发目的、行业、主要功能、技术特点必须优先来自业务理解。
- `操作手册.md/docx` 的说明、功能特点、系统要求、核心页面/流程、常见问题、术语表、全部项目自定章节及整体章节结构，必须优先来自模型确认后的业务理解。
- 操作手册不应只生成抽象的「功能列表」。模型应把路由、页面、按钮、输入框、列表、弹窗、状态提示、额度或权限规则等用户可见证据整理到 `manual_modules`，供脚本按通用操作手册骨架排版。最终成稿应是段落化用户手册，不是「进入方式 / 页面内容 / 操作步骤 / 结果反馈」式的字段列表。
- 如果缺少 `manual_modules`、`system_requirements`、`faq` 或 `glossary`，应回到业务理解阶段补充真实内容；脚本不得用分类模板缺省生成。
- 如果业务理解仍不充分，先提示用户补充产品说明，而不是直接生成泛泛描述。
