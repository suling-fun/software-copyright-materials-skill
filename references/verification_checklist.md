# 交付前验收清单

`软件著作权申请资料/正式资料/` 生成完成，不代表材料已无问题。本清单分为两部分：可自动执行的机械检查，以及必须由独立的人员或 agent 逐项核实、程序无法完成的检查。第 13 步「三轮验证」必须两部分均完成，缺一不可。

## 第一部分：程序化检查

执行以下命令：

```bash
python3 ${SKILL_DIR}/scripts/verify_materials.py --workdir 软件著作权申请资料
```

该脚本仅依赖标准库（`python-docx` 为可选增强，不可用时自动降级，不会中断执行）。逐项打印 `[PASS]`/`[FAIL]`/`[WARN]`，同时写入 `软件著作权申请资料/校验报告.md`；存在任一项 `FAIL` 即以退出码 `1` 结束，可直接接入自动化流程判断是否放行。

覆盖以下 8 类检查：

1. **文件完整性**：`正式资料/申请表信息.txt`、代码材料 docx、操作手册 docx 是否存在且非空。此项为最基础的底线检查，原因在于生成流程中途报错所产生的半成品文件不会自行消失，因此必须先确认三份文件均存在、且均非 0 字节。
2. **命名一致性**：申请表「软件全称」「版本号」与两份 docx 的文件名、页眉文字是否完全一致。软件全称与版本号若在某一环节出现偏差（例如正式生成时读取到旧的确认值），审核员看到的文件名、页眉与申请表将互不对应。该类问题在既往任务中实际出现过。
3. **页数一致性**：申请表「页数」字段与代码材料的实际页数是否一致。判据优先取 `正式资料/` 下同名 PDF 的页对象计数，即渲染完成后的真实分页（代码材料由 `render_code_pdf.py` 直接渲染，或由 Word/LibreOffice 转换，两者页数一致）；无 PDF 时降级为 docx 的显式分页符数量，该降级判据对代码材料准确，因其每页均由显式分页符断开。既往任务中曾出现页数字段取用理论总页数、而非前后各 30 页裁剪后实际渲染页数的情况，本项检查专门覆盖该回归。
4. **占位符/未确认内容残留**：申请表信息.txt 是否还留有「待用户确认」「待补充」字样；操作手册是否还有「截图预留」等占位文字却没有对应的 `skip` 记录。这两类残留表明生成流程在某一环节被跳过或未执行完毕，而正式材料已经产出。
5. **编造/套话内容检测**：操作手册正文是否命中一份可扩展的黑名单短语，包含既往任务中真实出现过的、脚本自身硬编码生成或模型编造插入的套话（如「账号进入、业务创建」「再选择或创建业务对象」），以及「总体设计」「详细设计」「测试案例」这类条件词——仅当业务理解的 `manual_extra_sections` 中没有对应章节时才判定为可疑。命中不代表必然存在问题，但须予以警觉，实际判断仍需人工核实（见第二部分）。
6. **截图健全性**（需要 `python-docx`）：操作手册内嵌图片的宽高是否超出 `build_docx_from_md.py` 里定义的 `IMAGE_MAX_WIDTH_IN`/`IMAGE_MAX_HEIGHT_IN` 约束。既往任务中出现过图片尺寸探测失败，导致截图被拉伸变形或跨页截断。本项检查能够拦截明显超限的情况，但无法拦截尺寸合规而内容与所属章节不对应的情况，后者属于第二部分的范围。
7. **申请表字段格式**：开发目的、面向领域/行业、软件的主要功能、软件的技术特点是否符合 `references/application_fields.md` 定义的长度限制，字符数统一用去除空格/换行后的有效字符数计算（复用 `generate_application_info.py` 的 `effective_len()`，避免另起一套可能不一致的计数口径）。
8. **确认记录完整性**：`environment`（仅当 DOCX 环境缺失时需要）、`business`、`code-selection`、`screenshot-method`、`application-fields`、`markdown` 六份确认记录文件是否都存在且对应确认字段为真。第七处 `project` 发生在材料目录建立之前，不留记录文件，本项无法覆盖。此项为最后一道防线，用于防止流程被跳过、正式材料在确认点未记录的情况下即行生成。

程序化检查通过，仅表明可见的格式与一致性无问题，不表明内容真实。内容真实性的核实由第二部分承担。

## 第二部分：必须由独立 agent/人工核实，程序无法判断

以下各项均曾在真实任务中出现问题，且无法通过改进脚本解决。此类核实所需的方法是打开真实证据逐项比对，而非模式匹配或字符串检查。

### 代码真实性核实

随机抽取代码材料 docx 中的若干代码片段（建议不少于 3 至 5 段，分散于文档前后不同位置），回到项目中打开对应的真实源文件，逐行核对内容是否完全一致。核对须实际打开源文件比对字符，不得以「读起来相似」作为通过依据。任何一段无法对应，均说明代码材料中混入了非真实源码，或抽取过程出现错位。

### 业务真实性核实

操作手册中每个模块描述的使用场景、操作步骤与结果反馈，是否能在项目的真实证据（源码逻辑、README、操作演示视频帧、用户提供的截图）中找到具体对应支撑。排查重点不在于该描述是否合理，而在于该描述是否来自真实证据。基于代码结构或业务理解作出的合理推测，若无证据支撑，实质上即属编造，行文通顺、表述专业亦不改变这一性质。

**README 不能作为最终依据。** 项目自述文件本身可能与实现不符，而手册若照抄，失实之责在材料。一次真实核实中查出八处此类错误：README 称趋势图在缺数据处「曲线断开」，实现是剔除该点后连成连续折线；称报告正文「不含任何统计数字」，而提示词保留了总评总分；称统计数值不外发，而报告请求实际携带时长、字数与三类问题词次数（此条涉及隐私声明，性质最重）；另有对比操作的实际步数、命题倒计时的起算时机、保存设置的写盘顺序、统计带某项读数的单位、题库字段的名称等，均与自述不符。

因此，凡属下列五类的陈述，一律回到源码逐条核对，并在核实结论中注明所依据的文件与行号：

- 数值口径：某项统计如何算出、单位为何、哪些数据被排除；
- 数据流向：哪些内容离开本机、送往何处、哪些不参与；
- 状态判定：缺数据、超限、前置条件未满足时界面的实际表现；
- 操作步数：自入口到结果实际需要几步，有无中间态；
- 控件文案：按钮、输入框、页签、菜单的名称是否与界面逐字一致。

### 截图匹配度核实

操作手册包含截图时，必须逐张独立打开每一张最终嵌入正式文档的截图图片，核实其与所在章节标题描述的模块是否确实对应。

**已发生的问题**：既往任务中，最初依据记忆与一次批量并行工具调用返回结果的顺序，直接为 10 张截图命名归档，结果全部与所属章节不对应。原因在于并行调用的返回顺序与发起调用时的文件顺序并不天然对应，依据记忆进行匹配缺乏可核验的依据，实质上属于推测。此后改为对每一张截图发起独立、隔离的查看调用，逐张核实内容后再命名归档，方才发现并纠正全部错位。

因此核实截图时：

- **不得**批量假设「文件名与调用顺序、结果顺序天然对应」。
- 必须对每一张最终产物截图单独发起一次独立的查看动作，边看边核对该图内容是否真的对应它所在章节的模块和标题，再确认归档。
- 最终截图有多少张，即须有多少次独立核实动作，不得以一次批量浏览代替。

### 行业/定位合理性核实

申请表的「面向领域/行业」「开发目的」「软件的主要功能」是否基于当前项目的真实证据（源码、README、实际功能、目标用户）作出判断，而非套用某一行业的关键词模板生成、更换项目名称后同样成立的泛化描述。判断标准如下：去除项目名称与具体功能词之后，考察该描述所余的信息量；若更换为任何一款同类软件均能成立，即说明该描述未真正扎根于当前项目。

### 操作手册文风核实

抽查操作手册是否存在带有机器生成特征的套话与模板轮换句式：即便已规避具体关键词黑名单检测，结构上是否仍高度雷同（例如每个模块的描述均为「用户点击 XX 按钮，系统弹出 XX 提示，完成 XX 操作」一类可无限复制并替换词语的固定句式），以及是否存在与当前项目无关的通用套话。此类问题通常可规避关键词检测，只能通过通读全文、比对不同模块之间的表达是否雷同予以发现。

### 设计取舍原因与边界情形核实

操作手册中「原因在于……」式的说明，须逐条回到项目证据核实该原因是否真实存在，而不是为满足格式补写的修饰性表述。判断方法与行业定位核实相同：将该句中的软件名与具体对象替换为任意另一款同类软件，若仍然成立，说明它没有扎根于当前项目，属于空话，必须删除或改写。

同时核实功能章节是否写明了可预见的边界情形。此类内容无法由代码结构泛泛推得，能够写出通常表明确实阅读过真实实现；反之，全篇只有正常路径、没有任何异常与边界描述的手册，基本可判定为照模板生成。

### 图注编号与配图对应核实

在逐张核实截图内容之后，另需核对编号体系本身：每幅图是否按「图 <章号>-<章内序号>」连续编号、章号是否与所在章一致、是否存在编号跳号或重复，以及每幅图的图注是否说明了该图要看的状态或结果，而不是把正文原句复述一遍。同一功能存在多个显著不同状态时（待命、进行中、结束后），是否分别配图并在图注中点明差异。

### 项目自定章节核实

必备章节之外的章节由模型自行判断设立，没有可对照的清单，因此这一项只能靠人工核实，程序无从判断。须同时核实两个方向。

**已设立的章节是否站得住**：逐章检查其 `reason` 是否对照三条判定标准给出了充分理由，`evidence` 指向的证据是否真实存在，正文内容能否回溯到该证据。凭推断编造出的模块路径表、数据目录表或配套文档清单，性质等同编造，必须删除整章。另需判断该章是否本就属于某个功能模块的正文而被不当外提。

**应当设立却缺失的章节**：反过来读项目。软件确实把统计数值呈现给用户，各功能章节却各自解释算法且口径不一，说明缺一章集中定义；软件确实在本机保存用户数据与凭据，全篇却找不到存放位置与数据流向，说明缺一章交代。这类缺口不会触发任何报错，只能靠通读项目与手册对照发现。

核实时不得以其他项目的章节构成作模板比对。不同软件的合理章节构成本就不同，两份手册章节不一致不构成问题，章节与项目实际不符才是问题。

### 强制要求独立性

第二部分的人工核实项，**必须**交由一个独立的验证 agent 执行，而不得由生成材料的同一个 agent 自行复核。委派时必须交付原始问题（例如「审计这份操作手册是否存在编造内容和截图错位」），而不是「验证此前生成的材料是否正确」；后者会诱导验证方带着材料应无问题的预期去确认，从而产生确认偏误。

发起验证的一方不得既是生成方又是唯一的验证方。生成材料的 agent 完成第 11 步正式生成、执行完毕第一部分程序化检查后，第二部分必须转交给一个独立的验证 agent，且该 agent 在开始核实前不应被告知「这些材料应无问题，请予确认」一类信息，而应按首次审查该材料的方式，从头核实。
