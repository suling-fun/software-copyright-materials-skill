# 交付前验收清单

`软件著作权申请资料/正式资料/` 生成完成，不代表材料没问题。本清单分两部分：能自动跑的机械检查，和必须靠独立的人/agent 逐项核实、程序永远做不到的检查。第 12 步「三轮验证」必须两部分都完成，缺一不可。

## 第一部分：程序化检查

运行：

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/verify_materials.py --workdir 软件著作权申请资料
```

只用标准库（`python-docx` 可选增强，不可用时自动降级，不会崩溃）。逐项打印 `[PASS]`/`[FAIL]`/`[WARN]`，同时写入 `软件著作权申请资料/校验报告.md`；只要有一项 `FAIL` 就以退出码 `1` 结束，可直接接入自动化流程判断是否放行。

覆盖以下 8 类检查：

1. **文件完整性**：`正式资料/申请表信息.txt`、代码材料 docx、操作手册 docx 是否存在且非空。这是最基础的底线——生成流程中途报错、写到一半的文件不会自己消失，必须先确认三份文件都在、都不是 0 字节。
2. **命名一致性**：申请表「软件全称」「版本号」与两份 docx 的文件名、页眉文字是否完全一致。软件全称和版本号一旦在某个环节走样（例如正式生成时读到了旧的确认值），审核员看到的文件名、页眉、申请表会互相对不上，这是本次任务里实际出现过的一类问题。
3. **页数一致性**：申请表「页数」字段与代码材料 docx 实际分页符数量（+1）是否一致。本次任务中曾经出现过页数字段取的是理论总页数而非前后各 30 页裁剪后的实际渲染页数，这一项检查专门盯住这个回归。
4. **占位符/未确认内容残留**：申请表信息.txt 是否还留有「待用户确认」「待补充」字样；操作手册是否还有「截图预留」等占位文字却没有对应的 `skip` 记录。这两类残留说明生成流程在某个环节被跳过或没跑完，正式材料却已经产出。
5. **编造/套话内容检测**：操作手册正文是否命中一份可扩展的黑名单短语，包含本次任务里真实出现过的、脚本自己硬编码生成或模型编造插入的套话（如"账号进入、业务创建""再选择或创建业务对象"），以及"总体设计""详细设计""测试案例"这类仅在业务理解未提供 `related_documents` 时才判定为可疑的条件词。命中不代表百分百有问题，但值得警觉——真正的判断仍需人工核实（见第二部分）。
6. **截图健全性**（需要 `python-docx`）：操作手册内嵌图片的宽高是否超出 `build_docx_from_md.py` 里定义的 `IMAGE_MAX_WIDTH_IN`/`IMAGE_MAX_HEIGHT_IN` 约束。本次任务里出现过图片探测尺寸失败导致截图被拉伸变形或跨页截断，这项检查能拦住明显超限的情况，但拦不住"尺寸合规但内容张冠李戴"——那是第二部分的工作。
7. **申请表字段格式**：开发目的、面向领域/行业、软件的主要功能、软件的技术特点是否符合 `references/application_fields.md` 定义的长度限制，字符数统一用去除空格/换行后的有效字符数计算（复用 `generate_application_info.py` 的 `effective_len()`，避免另起一套可能不一致的计数口径）。
8. **门禁记录完整性**：`environment`（仅当需要时）、`business`、`code-selection`、`screenshot-method`、`application-fields`、`markdown` 六个门禁文件是否都存在且对应确认字段为真。这是防止流程被跳过、正式材料在门禁未记录的情况下就生成出来的最后一道防线。

程序化检查通过，只说明"看得见的格式和一致性没问题"，不说明"内容是真的"。第二部分才是这份清单真正的价值所在。

## 第二部分：必须由独立 agent/人工核实，程序无法判断

以下每一项都曾经在真实任务里出问题，且都不是靠改进脚本能解决的——它们需要的是"打开真实证据、逐项比对"，而不是模式匹配或字符串检查。

### 代码真实性核实

随机抽取代码材料 docx 里的若干代码片段（建议不少于 3~5 段，分散在文档前后不同位置），回到项目里打开对应的真实源文件，逐行核对内容完全一致——是真的打开源文件比对字符，不是"读起来像"就算过。任何一段对不上，都说明代码材料里混入了非真实源码或抽取过程出现了错位。

### 业务真实性核实

操作手册里每个模块描述的使用场景、操作步骤、结果反馈，是否能在项目的真实证据（源码逻辑、README、操作演示视频帧、用户提供的截图）中找到具体对应支撑。重点排查的不是"这段描述合不合理"，而是"这段描述是不是从真实证据里来的"——模型基于代码结构或业务理解做出的"合理推测"，如果没有证据支撑，本质上就是编造，哪怕读起来通顺、专业。

### 截图匹配度核实

如果操作手册包含截图，必须逐张独立打开每一张最终嵌入正式文档的截图图片，核实它和所在章节标题描述的模块是否确实对应。

**本次任务的真实教训**：最初凭记忆和一次批量并行工具调用返回结果的顺序，直接给 10 张截图命名归档，结果全部张冠李戴——因为并行调用返回的顺序和发起调用时的文件顺序并不天然对应，凭记忆匹配等于是在猜。后来改成对每一张截图发起独立、隔离的查看调用，逐张核实内容后再命名归档，才发现并纠正了全部错位。

因此核实截图时：

- **不能**批量假设"文件名和调用顺序、结果顺序天然对应"。
- 必须对每一张最终产物截图单独发起一次独立的查看动作，边看边核对该图内容是否真的对应它所在章节的模块和标题，再确认归档。
- 有多少张最终截图，就要有多少次独立核实动作，不能用一次批量浏览代替。

### 行业/定位合理性核实

申请表的"面向领域/行业""开发目的""软件的主要功能"是否是基于当前项目的真实证据（源码、README、实际功能、目标用户）做出的判断，而不是套用某个行业的关键词模板生造出来的、换个项目名字也能通用的泛泛描述。判断标准很简单：把项目名字和具体功能词去掉之后，这段描述还剩下多少信息量——如果换成任何一个同类软件都成立，就说明这段描述没有真正扎根于当前项目。

### 操作手册文风核实

抽查操作手册是否存在"AI 味"套话、模板轮换句式——即使规避了具体关键词黑名单检测，结构上是否依然高度雷同（例如每个模块的描述都是"用户点击 XX 按钮，系统弹出 XX 提示，完成 XX 操作"这种可以无限复制粘贴换词的固定句式），以及是否存在与当前项目无关的通用套话。这类问题往往绕得过关键词检测，只有通读全文、对比不同模块之间的表达是否雷同才能发现。

### 强制要求独立性

第二部分这些人工核实项，**必须**交给一个独立的验证 agent 执行，而不是由生成材料的同一个 agent 自己"回头看一遍"。委派时必须给它原始问题（例如"审计这份操作手册是否存在编造内容和截图错位"），而不是"验证我刚才生成的材料是否正确"——后者会诱导验证方带着"应该没问题"的预期去确认，天然产生确认偏误。

发起验证的一方不能既是生成方又是唯一的验证方。生成材料的 agent 完成第 11 步正式生成、跑完第一部分程序化检查后，第二部分必须转交给一个独立的验证 agent，且该 agent 在开始核实前不应被告知"这些材料应该没问题，帮忙确认一下"，而应该被当作第一次审查这份材料一样，从头核实。
